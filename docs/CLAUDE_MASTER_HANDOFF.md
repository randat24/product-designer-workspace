## 1. Мандат и ожидаемый результат

Довести существующий продукт до надёжного, последовательного и проверяемого состояния. Сначала исправить обоснованные дефекты, затем проверить оставшиеся риски и подготовить следующий этап развития. Не ограничиваться планом для задач раздела 4.

**Поручено сейчас:** реализовать исправления F01–F05, провести ограниченную проверку однотипных ошибок, актуализировать документацию и выполнить доступную приёмку. По UX-гипотезам — собрать наблюдения и подготовить конкретные варианты. По новым продуктовым модулям — составить приоритетный backlog, а не реализовывать всю дорожную карту сразу.

Рутинные технические решения в этом объёме принимать самостоятельно. Разрешение пользователя из текущей сессии сохраняет силу. Новые внешние публикации, production-изменения, расходы и отправка реальных сообщений не подразумеваются передачей этого документа. При ограничении доступа закончить независимые локальные задачи и точно описать блокер.

**Результат:** обозримые изменения кода, воспроизводимые проверки, актуальный список оставшихся вопросов и следующий небольшой этап. «Идеально» здесь означает отсутствие известных незакрытых дефектов в согласованном объёме и честные границы проверки, а не обещание отсутствия всех возможных ошибок.

## 4. Обязательные исправления

### F01 · P1 · Надёжность автосохранения

**Доказательства — код:** `src/shared/ui/autosave.tsx`, хуки `useAutosave`, `useFieldAutosave`; `src/shared/lib/network.ts`; `src/domains/design/actions.ts`, `saveDecision`.

Выявленные механизмы:

1. `useAutosave` ждёт 800 мс; cleanup отменяет таймер без сохранения. При уходе с редактора до отправки можно потерять последнее изменение. `beforeunload` не защищает клиентские переходы Next.js.
2. `useFieldAutosave` делает best-effort запись при unmount, подавляя ошибку. Это не гарантия сохранения при offline/отказе.
3. Сценарий **A → B → A**: пока B сохраняется, пользователь возвращает A. Проверка `v === lastSaved.current` может пропустить отправку A; B запишется, а его ответ будет проигнорирован как устаревший. Интерфейс и БД могут разойтись.
4. Счётчик `round` после retry/reconnect остаётся ненулевым, а задержка задаётся как `round === 0 ? 800 : 0`. Следующие правки после восстановления могут постоянно обходить debounce.
5. Retry определяется сравнением текста ошибки с `t.autosave.failed`. Этот же текст используется, например, для невалидного `saveDecision`, что запускает автоматические повторы без изменения неверных данных.
6. `stale` отбрасывает обработку ответа, но не отменяет запись. `withTimeout` также не отменяет исходный запрос. Порядок записей при задержках и нескольких вкладках требует отдельной проверки, а не вывода только по статусу UI.

**Требуемое поведение:** последнее значение сохраняется либо пользователь остаётся с вводом и понятным выбором повтора/явного отказа. Применить решение, совместимое с Next.js App Router, ко всем потребителям общих хуков. Клиентские ссылки, программная навигация и Back/Forward должны быть включены в проверку.

Обрабатывать отдельно validation, permission/session, transient/network и conflict; текст для пользователя не должен управлять retry. Временные ошибки повторять контролируемо, валидацию — после исправления ввода. «Сохранено» означает подтверждённую запись актуального значения; «таймаут» означает неизвестный исход, а не доказанное отсутствие записи.

Не ограничиваться `void save()` при unmount, UI-флагом stale или общей подменой history без проверки всех путей. Выбрать минимально достаточную стратегию порядка записей; если нужна серверная проверка версии, обосновать её и добавить миграцию/тесты. Не разрабатывать полноценный realtime-редактор ради этого исправления. Не переносить чувствительный текст в постоянное браузерное хранилище без обоснования области, очистки и доступа.

**Приёмка:** воспроизвести быстрый уход раньше 800 мс; A→B→A при задержанной записи; несколько последовательных правок; timeout с поздним завершением; offline→online; повтор после восстановления с сохранением debounce; невалидное поле без бесконечных retry; отзыв права/истечение сессии. Проверять итог в базе или повторной загрузкой, не только toast. Прогнать также сценарий двух вкладок: результат и необходимость дополнительного механизма конфликтов оформить в V04; не считать этот механизм уже существующим или автоматически строить всю совместную работу.

Закрытие вкладки/процесса и сбой устройства не позволяют обещать абсолютную сохранность браузерной памяти: проверить доступное предупреждение и описать пределы гарантии. Результат незавершённой записи не выдавать за успех.

### F03 · P2 · Видимые ошибки действий и отсутствие ложного успеха

**Код:** `src/domains/design/actions.ts`, `createScreen`; `src/app/(app)/w/[ws]/p/[project]/screens/page.tsx`. Невалидные данные и ошибка insert завершаются простым `return`, форма не получает объяснения.

Добавить структурированный результат ожидаемого отказа, доступное сообщение и сохранение введённого имени. Использовать подход проекта (`useActionState` или подходящую адаптацию существующего механизма), без второй несогласованной системы ошибок. Общий Button уже использует `useFormStatus` и блокирует submit при pending: это поведение сохранить, а не считать отсутствующим.

Ошибка поля связана с полем; общая ошибка объявляется через доступный статус. Не раскрывать SQL/секреты. Не перехватывать `redirect` Next.js как ошибку. После успеха — переход к созданной записи. Блокировка кнопки не гарантирует серверную идемпотентность: при сетевом неизвестном исходе отдельно проверить безопасный повтор.

Ограниченно проверить соседние create/delete actions на такие же тихие отказы и исправить доказанные случаи. Каждый ранний return не является багом; проверить контракт вызывающего UI. Обработчик `useAction` сам по себе не распознает ошибку, если action вернул `void` как при успехе.

При повторном чтении найдены конкретные соседние места для этой проверки:

- `createDecision` и `addEvidence` в `src/domains/design/actions.ts` не проверяют результат вставки trace-связи; `createFlow` в `src/domains/flows/actions.ts` — результат вставки начального узла и связи с opportunity. Основная запись может быть создана, а дополнительная — нет. Определить, какие шаги составляют обязательный результат операции; показывать частичный результат или обеспечивать атомарность там, где она нужна. Повтор не должен создавать вторую основную сущность.
- `saveState`/`deleteState` в `src/domains/design/actions.ts` смотрят только на `error`; ноль затронутых строк не исключён. Сохранение несуществующей/недоступной записи нельзя выдавать за подтверждённую запись. Для delete определить допустимый идемпотентный результат отдельно. Образец проверки возвращённой строки уже есть в `src/shared/lib/supabase/tracked-update.ts`.

Это выводы по обработке результатов в коде; отказы ещё не воспроизведены. Исправлять наблюдаемый контракт результата, не навязывать общую транзакционную перестройку всех действий без необходимости.

**Приёмка:** валидное создание, поле из пробелов, отказ записи, потеря доступа, сохранение ввода, повтор после ошибки, отсутствие повторной отправки UI во время pending; для указанных соседних операций — отказ дополнительного шага и ноль затронутых строк. Есть регрессионная проверка отказа insert и видимого сообщения, а не только unit-тест схемы.

### F04 · P2 · Кейсы при недоступности базы и снятии публикации

**Код:** `src/site/cases-source.ts`, `getCases`: отсутствие URL/key, ошибка API или исключение возвращают встроенный список без регистрации причины. Успешный пустой ответ уже возвращает `[]`. Это намеренный прежний fallback, а не случайная опечатка; меняется его политика для production.

Разделить demo/test-режим и отказ рабочего источника. Рекомендуемая первая реализация: встроенные примеры только в явно определённом demo-режиме; production показывает корректную временную недоступность. Не строить дополнительное хранилище последнего успешного снимка без необходимости. Если используется такой снимок, задать срок актуальности и проверяемое удаление при снятии публикации.

Ожидаемые состояния источника различать: успешный непустой результат, успешный пустой результат, отсутствующая конфигурация, временный отказ. Ошибка БД не означает «кейс не существует»: не возвращать ложную 404 и не заменять рабочий список примерами. Не требовать одного HTTP-статуса для всех потребителей: статическая часть главной может работать, но состояние списка, detail, sitemap и OG должно быть осмысленным и проверенным.

Сохранить uk/en, сортировку, `status = published`, обновление после публикации и исключение sample из поискового индекса. Добавить безопасную серверную диагностику категории/кода ошибки без контента и ключей. Проверить неправильную структуру снимка до рендера: приведение TypeScript не валидирует JSON; фактическая порча данных пока не установлена.

**Все потребители:** главная, список кейсов, detail, metadata, `generateStaticParams`, `src/app/sitemap.ts`, `src/app/og/route.tsx`, публикация в `src/domains/cases/actions.ts`.

Настроить явную тестовую фикстуру/режим или корректную зависимость сборки от тестовой БД. ## 5. Дизайн: что проверить и какие решения подготовить

## 7. Production: сначала наблюдение, затем выводы

При наличии авторизованного доступа проверить read-only: соответствие Vercel deployment текущему commit; статус сборки/логи; имена и области переменных по `.env.example` и `RELEASE_CHECKLIST.md`; применённые миграции по фактическому списку; RLS/гранты; Auth URL/redirect/SMTP; intake secret и настройки принимающего workspace; Turnstile и уведомления, если они включены; домен, canonical, preview-noindex, опубликованные кейсы.

Не применять старые номера миграций вслепую и не считать дату в имени миграции доказательством её развёртывания. Не выводить значения секретов. Перед изменениями Supabase проверить актуальную документацию/инструкции и совместимость с версией проекта.

Вход, восстановление пароля, заявку, PDF, публикацию/снятие и удаление тестировать на локальном или согласованном тестовом окружении, с тестовыми адресами и изолированными данными. Read-only production-проверка не подразумевает отправку реальных писем, запись тестовых заявок или деплой. Если соответствующее разрешение уже получено в текущей сессии, не запрашивать его повторно.

Без доступа завершить F01–F05 и локальную приёмку; production пометить «не проверено», указать конкретный недостающий доступ и действие владельца. Не обещать «готово к production» только на основании локальных тестов.

## 8. Направление и этапы развития

**Рекомендуемое позиционирование:** рабочее пространство, которое связывает исследование с решениями и собирает из работы понятный результат для коллеги, клиента и портфолио. Основной путь: **вводные → исследование → выводы → решение → проверка → передача/публикация → архив**.

Портфолио и заявки уже образуют внешний вход/выход; развивать эту связь без превращения продукта в универсальную CRM. PRD называет и работающего дизайнера, и junior первичными сегментами. Предложение для первого пилота — соло-дизайнер с реальным проектом, обучение как необязательная помощь. Это рекомендация, а не принятое владельцем решение.

Ниже порядок **результатов**, не замена существующим фазам 0–12, номерам миграций или структуре БД. Сроки не задаются без оценки объёма и исполнителей.

| Этап | Минимальный объём | Критерий перехода |
|---|---|---|
| A Надёжность | F01–F05, критические результаты V03–V06, доступные проверки среды и документация | На тестовом проекте нет известной тихой потери/ложного успеха; права и граница публикации проверены; пределы восстановления и недоступные production-проверки записаны |
| B Первое полезное использование | Развить демо/next actions; один востребованный шаблон; понятный старт и ограниченный импорт с предпросмотром/отчётом | Новый пользователь самостоятельно проходит выбранный путь и объясняет пользу; ошибки импорта и повторы не создают незаметных дублей. Сначала малый пилот, затем расширение |
| C Передача результата | Развить Phase 8a через Phase 11: готовность экрана, читаемая спецификация/экспорт, сводка решений/вопросов; редактура существующего кейса | Коллега понимает что делать, почему, какие состояния нужны и что ещё открыто. Не повторный JSON-export и не второй PDF заявки. Read-only review вводить только с выбранной моделью доступа/отзыва |
| D Проверка решений | Нужный минимум Phase 6 + Phase 10: одна гипотеза, сценарий проверки, наблюдение, решение подтвердить/изменить/отклонить | Завершён один цикл, вывод влияет на связанный экран/решение; результаты содержат источник, период и ограничения, а не придуманную причинность |
| E Совместный review | При спросе: приглашения/роли UI, комментарии к артефакту, запрос и завершение ревью | Автор и коллега завершают согласование; права соблюдены, доступ отзывается; уведомления управляемы. Совместный ввод в одно поле не обязателен |
| F Автоматизация | Сначала одна нужная интеграция либо одна AI-операция на проверяемых данных | Экономия времени сохраняется после человеческой проверки результата; источники верны, доступы изолированы, стоимость измерена |

Этапы C/D/E могут менять порядок по наблюдению пилота. Массовое внедрение всего списка не является критерием завершения текущего задания. Текущий roadmap ставит AI первым после MVP; рекомендация этого ревью — сначала надёжность и ценность ручного цикла, затем автоматизация доказанных затратных операций.

### Метрики без формального заполнения

`MVP.md` предлагает пилот 10–15 дизайнеров, а MVP/PRD — ориентиры ≥80% инсайтов с источником и ≥60% экранов с upstream-связью. Это плановые гипотезы, не фактические результаты. Знаменатель — реальные активные проекты и соответствующие сущности; демо/синтетические данные исключить. Семантическую полезность связей оценивать выборочно, а не только считать их наличие.

До пилота определить активацию (первое полезное решение с проверяемым источником), начало/конец замера времени, период повторного использования и причины остановки. Дополнить скоростью поиска обоснования и качеством передачи коллеге. Собирать минимум технических событий без текста интервью и контактов. Для hero/заявки измерять понимание и завершение сценария; малый качественный пилот не выдавать за статистически доказанный рост конверсии.

### Перспективные функции без дублирования

| Идея | Опора на существующее | Когда и как оценивать |
|---|---|---|
| «Почему существует экран?» | Trace panel, evidence, Decision Log | B–C: человек быстро находит реальное обоснование, а не автоматически украшенный текст |
| «Что затронет изменение?» | Тот же граф связей | D: после отклонения инсайта корректно выделяются решения/экраны для проверки |
| «Готово к разработке?» | Состояния экранов и next actions | C: показывает конкретные пробелы, без второго несогласованного процента |
| Сводка для клиента | Решения, ограничения и следующий шаг | C: понятна человеку вне проекта; содержит только разрешённые материалы |
| Сборка кейса | `case_studies`, uk/en-снимок и статусы | C: меньше повторного написания, есть редактура, предпросмотр и проверка приватности |
| Шаблоны типов проекта | Демо/бриф/гайд и существующий импорт | B: ускоряют повторяющийся сценарий, не принуждают проходить ненужные этапы |
| Сравнение вариантов/противоречий | Alternatives решений и evidence | D: сохраняет основания выбора и конфликтующие данные; AI необязателен |

**Figma и AI:** ссылки/превью уже частично есть; полезное расширение — актуальность источника и передача в один выбранный трекер. Начать с одностороннего обмена; двусторонняя синхронизация требует правил повторов, конфликтов и удаления. AI предлагает цитаты, синтез, спецификацию или кейс с проверяемыми источниками; человек принимает отдельные предложения. Нужны контрольный набор качества, отклонение результата, изоляция workspace, правила передачи персональных данных, лимиты затрат и обработка инструкций в импортированном тексте как данных. Не выдумывать интервью/метрики ради красивого результата.

**Отложить до спроса:** свой графический редактор, универсальный таск-трекер/whiteboard, сложный realtime, marketplace, нативное мобильное приложение, биллинг/тарифную сетку. Phase 9 Design System остаётся возможным этапом, но сначала доказать, чем он дополняет Figma и handoff.

## 9. Порядок исполнения и проверка результата

1. Прочитать действующие инструкции репозитория; проверить HEAD/diff и доступные инструменты. Сохранить посторонние изменения. Не повторять уже исправленное по старым документам.
2. Зафиксировать минимальное воспроизведение F01/F03 и политику данных для F04; выбрать локальный/test контур. Внешний доступ не нужен для начала исправлений.
3. Выполнить F01+F02, затем F03, F04 и F05 небольшими обозримыми изменениями. Добавлять регрессионные тесты для поведения, не тесты, повторяющие реализацию.
4. Проверить U-пункты на реальных экранах и заполнить V-матрицу. Доказанные новые дефекты описать отдельно по серьёзности; не скрывать их в общей косметической переработке.
5. Обновить статусы документации и подготовить ближайший этап B/C по результатам. Продуктовые развилки представить конкретными вариантами, не общим вопросом «что делать дальше?».

### Команды

Из корня проекта после изменений:

```bash
npm run typecheck
npm run lint
npm test
npm run build
```

Для изменённых браузерных сценариев — существующий Playwright (`npm run e2e`), конфигурация `playwright.config.ts`, образец тестовой Supabase в `.github/workflows/ci.yml`. | Отказы/доступ | Offline, медленный ответ, read-only, истечение сессии, другой workspace | Управляемый отказ, данные не раскрываются и не теряются молча |
| Восстановление/передача | Только в проверяемом выбранном объёме V03/V07 | Реальное восстановление тестового примера либо честно описанное ограничение |

Не перебирать механически все комбинации всех экранов: общие компоненты проверять репрезентативно, рискованные сценарии — прицельно. Axe, скриншоты и отсутствие overflow не заменяют прохождение задачи. Эмуляция Chromium не доказывает поведение iOS Safari; ограничения платформы указывать.

### Документация и формальное завершение

`QUALITY_REVIEW.md` содержит исторические проблемы и поздние отметки исправления; `ROADMAP.md` отстаёт шапкой от README; в Later остаются части уже начатого портфолио; MVP содержит старые допущения rich text/auth/mobile. Сверить с кодом, сохранить историю и разделить статусы **реализовано / проверено локально / выложено / проверено в production**. Не снимать `sample`, не выдумывать реальные кейсы, показатели, фотографии и отзывы ради завершённости.

**Завершено исправление** — код изменён, необходимая регрессия проходит, побочные сценарии проверены и ограничения записаны. **Готово к выпуску** — дополнительно проверены миграции/конфигурация, доступы, production-предпосылки и способ отката. **Выпущено** — только после фактического разрешённого деплоя и проверки, не после локального build. Недоступные проверки оставлять открытыми, не заменять зелёной галочкой.

Финальный отчёт Claude:

```text
Commit/ветка:
F01–F05: статус → что изменено → доказательство → остаточный риск.
Дополнительные доказанные дефекты: отдельно, с приоритетом.
U01–U07: наблюдение/прототип/решение; что требует выбора владельца.
V01–V10: есть и проверено / частично / не найдено / заблокировано + ссылка.
Проверки: команды, окружение, выполнено/упало/пропущено; причины пропусков.
Production: что действительно проверено, какие доступы/действия отсутствуют.
Изменённые файлы и diff/commit; миграции и откат, если применимо.
Следующий этап: 3–5 небольших задач с целью, зависимостями и приёмкой.
```

Не закрывать работу отчётом «всё исправлено», если оставшиеся обязательные сценарии не выполнялись. При этом отсутствие production-доступа не должно мешать завершить доступные исправления и подготовить результат для ревью.

## 11. Поэтапные чек-листы для исполнения

### Как отмечать работу

- Все пункты ниже изначально открыты: добавление этого документа не означает выполнение исправлений.
- `[x]` ставить только после выполнения указанного действия и записи доказательства: файл/diff, название прошедшего теста, скриншот или результат конкретной проверки. Для запуска/проверки указывать дату, среду и проверенный HEAD.
- Заблокированный пункт оставить `[ ]` и приписать `БЛОКЕР: причина; что требуется; какие независимые задачи продолжаются`.
- Неприменимый пункт оставить `[ ]` и приписать `Н/П: обоснование`. Отменённый продуктовый вариант не помечать реализованным.
- Отдельно указывать результат проверки: «выполнена, найден дефект» не равно «дефект исправлен». U-пункт может завершиться обоснованным решением оставить текущий интерфейс.
- Этап с незавершённым обязательным исправлением не объявлять закрытым. При этом блокер одного этапа не останавливает независимые этапы.
- Рядом с каждым этапом вести короткую запись: `Статус | commit | доказательства | открытые пункты`. Новые выявленные дефекты получать отдельный ID, не скрываться под общей галочкой.

**Зависимости:** подготовка → исправления → общая техническая приёмка → полный контрольный сценарий → итоговая передача. Дизайн, инвентаризацию V и read-only проверку production можно вести параллельно независимым работам. Будущие этапы B–F выбираются после текущего пакета; они не являются условием закрытия всех F-исправлений.

- [ ] C07.10 **V10:** при наличии доступа проверить тарифы/квоты/лимиты и настройки anti-spam; без доступа записать конкретные неизвестные, не подставлять предположения.
- [ ] C07.11 Заполнить итоговую таблицу V01–V10 статусом, доказательством и минимальной следующей задачей; подтверждённые дефекты вынести отдельно от продуктовых возможностей.

**Выход:** по каждому V-ID известно, что реализовано и проверено, что частично и что недоступно проверке. Сам аудит может завершиться с открытыми продуктовыми задачами.

### Этап 8. Проверить production в пределах доступа

Read-only пункты можно выполнять раньше параллельно исправлениям. Они относятся к конкретному существующему deployment и не доказывают, что новый diff уже выложен.

- [ ] C08.1 Подтвердить авторизованный доступ к нужным Supabase/Vercel; при отказе записать точный блокер и продолжить независимые работы.
- [ ] C08.2 Записать проверяемый deployment, commit и статус сборки; сопоставить логи с этой версией.
- [ ] C08.3 Проверить наличие/области Production/Preview переменных без вывода значений; сверить фактические миграции с репозиторием.
- [ ] C08.4 Проверить RLS/гранты, публичные кейсы, Auth URL/redirect и конфигурацию почты; отличать чтение настройки от успешного функционального теста.
- [ ] C08.5 Проверить конфигурацию приёма заявок, принимающего workspace, Turnstile и уведомлений, если они включены; сверить домен/canonical/preview-noindex.
- [ ] C08.6 Функционально проверить вход, восстановление пароля, заявку и PDF на изолированном контуре; реальные письма/production-записи выполнять только при имеющемся разрешении.
- [ ] C08.7 Записать, что проверено именно в production, а что только локально/test; сформировать конкретный список оставшихся внешних действий.

**Выход:** проверка среды имеет доказательства или точные блокеры. Не начинать деплой только ради закрытия чекбокса; политика выпуска остаётся из разделов 1 и 9.

### Этап 9. Пройти один полный контрольный проект

Сначала использовать синтетический проект и тестовые аккаунты. Реальный пилот требует выбранного участника и согласованного доступа; не связываться с людьми автоматически.

- [ ] C09.1 Создать тестовую заявку и получить PDF; преобразовать её в проект, если этот путь включён в выбранный сценарий.
- [ ] C09.2 Проверить бриф, исследование, участника и интервью; сохранить данные, уйти и вернуться.
- [ ] C09.3 Создать цитату/наблюдение, инсайт, проблему и возможность; проверить необходимые trace-связи и поиск источника в обратном направлении.
- [ ] C09.4 Создать flow, экран и состояния; зафиксировать решение, альтернативу и доказательство, проверить доступную мобильную работу.
- [ ] C09.5 Проверить передачу результата в существующем объёме; отсутствующий будущий handoff-модуль записать как ограничение, не создавать его ради прохождения теста.
- [ ] C09.6 На тестовом контуре проверить подготовку доступного снимка кейса, публикацию и снятие; убедиться, что в него не попали приватные сведения.
- [ ] C09.7 Выгрузить существующий экспорт, архивировать и вернуть проект; проверить сохранность связей. Не смешивать это с восстановлением удалённого проекта.
- [ ] C09.8 Записать итог сценария, неудобные переходы и открытые ограничения; выделить действительно блокирующие дефекты.

**Выход:** известен результат всего жизненного цикла, а не только работоспособность отдельных страниц. Будущие модули не притворяются существующими.

### Этап 10. Закрыть текущий пакет и передать результат

- [ ] C10.1 Сверить F01–F05 с целевыми регрессиями; оставшиеся обязательные пункты явно перечислить, не закрывать их общей фразой.
- [ ] C10.2 Обновить документацию по фактическому коду, сохранив историю: README, ROADMAP, MVP, QUALITY_REVIEW и DESIGN-SYSTEM в затронутой части.
- [ ] C10.3 Устранить противоречия про mobile, экспорт, уже реализованные кейсы и статусы фаз; различать «реализовано / проверено / выложено».
- [ ] C10.4 Просмотреть итоговый diff на посторонние изменения, секреты, выдуманный контент и необоснованный редизайн; подготовить небольшие логические изменения для ревью.
- [ ] C10.5 Приложить результаты команд, выполненные/пропущенные сценарии и относящиеся к UX скриншоты; указать проверенный commit и среду.
- [ ] C10.6 При изменении данных/конфигурации описать миграции, зависимости и безопасный откат; не обещать откат данных простым возвратом кода.

- [ ] C10.8 Сформировать следующий этап из 3–5 задач, каждая с пользователем/проблемой, зависимостями, критерием результата и границей объёма.

**Выход:** текущий пакет готов к ревью с честным статусом. «Выпущено» писать только после отдельного фактически выполненного разрешённого выпуска и проверки; успешный локальный build этого не означает.

### Этап 11. Развитие после текущего пакета — выбирать по пользе

Этап A дорожной карты покрывается исправлениями и проверками выше. Ниже чек-листы B–F из раздела 8: они **не являются поручением реализовать всё сейчас**. Не дублировать существующие сущности. Сначала выбрать ближайший этап по данным пилота; порядок C/D/E допускает изменение.

**B. Первый полезный результат и пилот**

- [ ] B.1 Выбрать первый сегмент и одну задачу пилота; заранее определить активацию, период наблюдения и метрики, исключив демо из расчётов.
- [ ] B.2 По наблюдаемому препятствию доработать существующий старт/демо/next actions; добавить один нужный шаблон, а не каталог всех методик.
- [ ] B.3 Если нужен импорт, определить поддерживаемый формат, предпросмотр, пропуски и безопасный повтор; проверить на реальном для задачи примере без персональных данных.
- [ ] B.4 Провести согласованный пилот, записать самостоятельное прохождение, время и причины остановки; принять решение о следующем этапе.

**Выход B:** пользователь получает полезное связанное решение без сопровождения автора; критерии результата оценены, а не заменены количеством созданных карточек.

**C. Передача результата**

- [ ] C.1 Выбрать получателя и минимальный состав пакета: задача, обоснование, состояния, решения и открытые вопросы.
- [ ] C.2 Собрать пакет из существующих спецификаций/связей; реализовать выбранный читаемый формат и проверку готовности без второго редактора тех же данных.
- [ ] C.3 Развить редактуру/предпросмотр существующего кейса; для read-only review сначала определить доступ и отзыв, если такая функция выбрана.
- [ ] C.4 Проверить понимание пакета человеком вне проекта и отсутствие лишних приватных материалов; записать ограничения экспорта и ссылок.

**Выход C:** получатель понимает результат без дополнительных устных объяснений автора.

**D. Проверка решений**

- [ ] D.1 Выбрать одну гипотезу и связанный экран/решение; определить ожидаемое наблюдение до тестирования.
- [ ] D.2 Реализовать минимальную запись сценария, результата и источника; не добавлять весь набор сущностей Definition сразу.
- [ ] D.3 Поддержать подтверждение/изменение/отклонение и противоречащие данные; сохранить историю основания решения.
- [ ] D.4 Пройти цикл проверки и показать, какое решение изменилось; метрики снабдить периодом, источником и ограничениями интерпретации.

**Выход D:** проверка меняет или обоснованно подтверждает решение, а не заканчивается отдельным несвязанным отчётом.

**E. Совместный review**

- [ ] E.1 Подтвердить спрос пилота и определить матрицу ролей/приглашений, не добавляя сложный realtime по умолчанию.
- [ ] E.2 Реализовать приглашение, отзыв доступа и выбранный сценарий комментария/запроса ревью к конкретному артефакту.
- [ ] E.3 Добавить завершение замечания и управляемые уведомления; проверить удалённые/отозванные приглашения и аккаунты.
- [ ] E.4 Пройти сценарий автор→рецензент→решение; проверить читателя, другой workspace и конфликты действий.

**Выход E:** согласование завершается внутри продукта с корректными правами и без лишнего шума.

**F. Интеграции и AI**

- [ ] F.1 Выбрать одну подтверждённую затратную операцию: интеграцию с источником/трекером либо AI-помощь; определить исходное время и качество.
- [ ] F.2 Для интеграции определить направления, повтор, конфликт и удаление; начать с минимального обмена поверх уже существующих Figma-ссылок/превью.
- [ ] F.3 Для AI определить допустимые данные, источники, принятие/отклонение, контрольный набор качества, изоляцию workspace и предел расходов.
- [ ] F.4 Проверить неверные/недоступные источники, инструкции внутри импортированного текста и отказ внешнего сервиса; сохранить управляемый ручной путь.
- [ ] F.5 Измерить экономию времени с учётом проверки человеком, качество и стоимость; расширять только при доказанной пользе. Пункты невыбранного направления отметить Н/П, а не выполнять обе ветки автоматически.

**Выход F:** автоматизация экономит работу без потери проверяемости и контроля пользователя.
