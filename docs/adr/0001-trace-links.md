# ADR-0001 · Traceability через единую таблицу `trace_links`

Статус: **Accepted** (Phase 1) · Дата: 2026-09-29

## Контекст
Главная ценность продукта — ответ на вопрос «почему этот экран существует?». Цепочка включает ~15 типов сущностей (интервью, цитата, наблюдение, инсайт, боль, возможность, гипотеза, функция, сценарий, экран, решение, тест…), многие связи many-to-many, и набор типов будет расти по фазам.

## Решение
- Смысловые связи «доказательство → вывод» хранятся в одной таблице `trace_links (source_type, source_id, target_type, target_id, relation)`.
- Направление всегда upstream → downstream.
- Допустимые комбинации — справочник `trace_relation_rules`; составной FK из `trace_links` на него отклоняет недопустимые пары на уровне БД.
- Существование обеих сущностей в том же проекте проверяет триггер `trace_links_validate` через реестр `entity_types`.
- Удаление сущности чистит связи триггером `trace_cleanup`, который подключается функцией `attach_domain_table`.
- Обход графа — `trace_graph()` (recursive CTE, защита от циклов, лимит 500 рёбер, RLS вызывающего).
- Жёсткое владение (интервью → участник, узел → сценарий) остаётся обычными FK.

## Последствия
+ Новые типы сущностей добавляются строками в `entity_types` и `trace_relation_rules`, без миграций существующих связей.
+ «Всё выше этого экрана» — один запрос.
− Нет нативных FK на полиморфных колонках: целостность держится на триггерах. Покрыто pgTAP-тестами (`supabase/tests/database/02_trace.test.sql`).
− Динамический SQL в валидаторе: имена таблиц берутся только из `entity_types` и экранируются `%I`.
