# Заявка на проєкт (Client Project Intake): архитектура

Статус: **реализовано** (миграции 017–018, форма uk/en, PDF, раздел «Заявки», конвертация в проект, уведомление по e-mail).
Что сознательно оставлено на потом — §15. Решения владельца — §16, настройка production — §14.

Цель: клиент один раз описывает проект на сайте → в инструменте появляется структурированная **заявка** (не проект),
из которой одним действием собирается проект с заполненным брифом и конкурентами. Всё, что сказал клиент, остаётся
помеченным как **данные клиента** и не смешивается с исследованием дизайнера.

## 1. Аудит: что уже есть и что переиспользуем

| Что есть | Где | Как используем |
|---|---|---|
| Пространства, роли `owner/editor/viewer`, `is_workspace_member()` | `core.sql` | Заявки и клиенты принадлежат пространству; RLS по той же функции |
| Один владелец, одно пространство в production (`randat24-…`, личное) | БД | Публичная форма пишет в одно «принимающее» пространство (настройка, не хардкод) |
| `projects` (+ `archived_at`), `project_briefs` (продукт, бизнес, аудитория, проблема, цели, сроки, ссылки, текущий продукт, ограничения) | `core.sql`, `briefs.sql` | Конвертация заполняет бриф; новых таблиц для брифа не нужно |
| `competitors` (имя, url, сильные/слабые стороны, позиционирование…) | `competitors.sql` | Конкуренты из заявки становятся карточками конкурентов с пометкой «от клиента» |
| `activity_log` + `log_activity()` | `activity.sql` | Журнал статусов заявки — тем же триггером |
| Хранилище: приватный бакет `attachments`, только картинки, 10 МБ, путь `project_id/…`, политики по членству | `competitors.sql` | Файлы заявок — отдельный приватный бакет по тому же образцу (фаза 2, см. §6) |
| Публичный сайт `/uk`, `/en`, middleware пропускает только эти локали | `src/app/(site)` | Новые маршруты `/uk/start-project`, `/en/start-project` |
| Аналитика: `track()`, типизированный список событий, Consent Mode, `page_location` без query | `src/site/analytics` | События воронки без персональных данных |
| Страница «Конфіденційність» | `/{locale}/privacy` | Дополняется разделом о заявках (текст на проверку владельцу) |
| PDF резюме: Chromium при сборке (`scripts/build-cv.ts`) | — | Не подходит для рантайма на Vercel → другой движок, §7 |
| Серверного ключа Supabase **нет** ни в коде, ни в Vercel; все запросы идут от анонимного или вошедшего пользователя | `src/shared/lib/supabase` | Публичная запись — через одну функцию в БД, защищённую секретом сервера, §5 |
| Интерфейс инструмента на украинском (`uk.ts`), сайт — uk/en | — | Форма и PDF — uk/en, раздел «Заявки» в инструменте — uk |

Чего нет: серверного ключа, почтового провайдера, Turnstile, ограничения частоты запросов, клиентских сущностей.

## 2. Модель данных

```
workspaces ─┬─ clients ──────────────┐
            │                         │ 1..n
            ├─ project_requests ◄─────┘
            │     ├─ project_request_competitors   (n, ≤ 10)
            │     ├─ project_request_references    (n, ≤ 10)
            │     ├─ project_request_links         (n, ≤ 15: текущий продукт и материалы)
            │     ├─ project_request_notes         (внутренние заметки)
            │     ├─ project_request_documents     (снимки: бриф v1, позже скоуп, смета…)
            │     └─ project_request_files         (фаза 2, файлы)
            ├─ request_counters (workspace, year) → REQ-2026-0001
            ├─ intake_settings (принимающее пространство, вкл/выкл, версия политики)
            └─ projects.source_request_id → project_requests (одна заявка → не более одного проекта)
```

### `clients`
Клиент пространства, а не пользователь системы (позже — клиентский портал: `auth_user_id` nullable).
`name`, `email`, `company`, `role`, `phone`, `telegram`, `website`, `preferred_channel` (`email|telegram|phone|other`),
`preferred_channel_note`. Уникальность `(workspace_id, lower(email))`: повторная заявка того же человека
привязывается к тому же клиенту, контакты обновляются только пустые → ничего не перетирается молча.

### `project_requests` — сама заявка
Типизированные колонки, а не один jsonb: по ним фильтруем, сортируем и переносим в проект; CHECK-ограничения в БД.

| Группа | Колонки |
|---|---|
| Служебные | `id uuid`, `workspace_id`, `client_id`, `code` (`REQ-2026-0012`, уникален в пространстве), `status`, `locale`, `form_version`, `submitted_at`, `archived_at`, `created_at`, `updated_at` |
| Тип и имя | `project_types text[]` (ключи из конфига), `project_type_other`, `project_name`, `project_name_unknown` |
| Текущий продукт | `has_existing boolean`, `existing_url`, `existing_description`, `existing_dislikes`, `existing_works_well`, `existing_must_change` |
| Описание и цели | `summary`, `what_it_does`, `problem`, `why_now`, `goals text[]`, `goal_other` |
| Аудитория | `audience`, `primary_users`, `geography`, `market` (`b2b|b2c|b2b2c|internal|unknown`), `demographics`, `pain_points` |
| Скоуп и материалы | `scope text[]`, `scope_needs_advice boolean`, `materials text[]` |
| Бюджет (приватно) | `budget_range` (ключ конфига или `custom`/`undecided`/`estimate`), `budget_min`, `budget_max` (numeric), `budget_currency` (`USD|EUR|UAH`), `budget_note` |
| Сроки | `start_preference` (`asap|2_weeks|month|1_3_months|later|undecided`), `has_deadline`, `deadline_date`, `deadline_reason` |
| Прочее | `additional_info` |
| Согласие | `consent_at`, `privacy_policy_version` |
| Доступ клиента к PDF | `client_token_hash` (sha256), `client_token_expires_at` |
| Связь с проектом | через `projects.source_request_id` (обратная ссылка не дублируется) |

Длинные тексты ≤ 4 000 символов, короткие ≤ 200, URL ≤ 500, только `http(s)`, без `user:pass@`.
Все ограничения дублируются: zod на сервере + CHECK в БД.

### Жизненный цикл (`request_status`)
`submitted → reviewing → qualified → accepted → converted`; из любого до `converted` → `declined`.
`draft` в БД не храним: черновик живёт в браузере (§8). Архив — отдельная отметка `archived_at`, не статус:
отклонённую или принятую заявку можно убрать из списка, не теряя её статуса.
`converted` ставит только функция конвертации; руками его не выбрать и не снять.

### Документы: `project_request_documents`
`document_type` (`project_brief`; позже `discovery_summary`, `scope`, `proposal`, `estimate`, `sow`, `design_brief`),
`version int`, `locale`, `content jsonb` (снимок данных на момент создания), `template_version`, `generated_at`, `created_by`.
`unique (request_id, document_type, version, locale)`. Триггер запрещает UPDATE: новая редакция = новая строка
с `version + 1`, старые не перезаписываются. «Бриф проекта — версия 1» создаётся в той же транзакции, что и заявка.

### Номер заявки
`request_counters (workspace_id, year, last_value)`: `insert … on conflict do update set last_value = last_value + 1 returning`
— одна атомарная операция, без гонок; номер `REQ-{год}-{4 цифры}`. Первичный ключ остаётся uuid.

## 3. Заявка → проект

Публичная отправка создаёт **клиента + заявку + документ «бриф v1»**. Проект не создаётся.
Действие «Сделать проектом» (функция `convert_project_request`, только `editor+`, одна транзакция):

| Из заявки | Куда | Пометка |
|---|---|---|
| имя проекта | `projects.name`, slug | — |
| описание, что делает, зачем сейчас | `project_briefs.product_description` | «из заявки клиента» |
| проблема | `project_briefs.problem` | «из заявки клиента» |
| цели | `project_briefs.goals` | «из заявки клиента» |
| аудитория, пользователи, гео, боли | `project_briefs.target_audience` | «из заявки клиента — не проверено исследованием» |
| текущий продукт и что не нравится | `project_briefs.existing_product` | «из заявки клиента» |
| сроки, дедлайн | `project_briefs.timeline_start/end` | — |
| ссылки, референсы | `project_briefs.links` | тип `reference` |
| конкуренты | `competitors` (имя, url, сильные = «нравится», слабые = «не нравится») | `origin = 'client'`, бейдж «Від клієнта» |
| скоуп | `project_briefs.business_requirements` (текстом) | «ожидания клиента» |
| бюджет | **не копируется**: остаётся в заявке, в проекте — ссылка «Коммерческое» на заявку | приватно |

**Как отличать данные клиента от находок дизайнера** — без дублирования:
- в `project_briefs` новая колонка `client_input jsonb`: исходные формулировки клиента по полям.
  Пока текст поля совпадает с исходным, рядом бейдж «Со слов клиента (REQ-2026-0012)». Дизайнер переписал → бейдж
  исчезает, исходник доступен по ссылке «Как сказал клиент»;
- в `competitors` новая колонка `origin` (`designer` по умолчанию | `client`);
- инсайты, боли, исследования **не создаются**: это работа дизайнера, а не утверждения клиента.

Изменения существующих таблиц — только добавление nullable-колонок с безопасными значениями по умолчанию
(`projects.source_request_id`, `project_briefs.client_input`, `competitors.origin`). Существующие данные не трогаются.

## 4. RLS и доступ

| Таблица | anon | участник пространства | editor+ | owner |
|---|---|---|---|---|
| `clients`, `project_requests`, дочерние | **нет доступа** | чтение | изменение статуса, заметки, конвертация, архив | удаление |
| `project_request_documents` | **нет** | чтение | создание новой версии | — |
| `request_counters`, `intake_settings` | нет | нет (настройки — owner) | — | изменение |

У анонимной роли нет ни одного права на эти таблицы. Публичная запись — только через функцию (§5), чтение клиентом
своего брифа — только через функцию с токеном (§7). Бюджет видят участники пространства; при желании ограничим
до `owner` (решение 5). Тесты pgTAP: аноним не читает и не пишет ни одну таблицу, участник чужого пространства не видит
заявки, `viewer` не меняет статус, `converted` руками не ставится, документ нельзя изменить.

## 5. Публичная отправка и защита от спама

```
Браузер ──POST (server action)──► Next.js на Vercel ──rpc(submit_project_request, payload, secret, ip_hash)──► Postgres
           honeypot, время,        zod-валидация,                     security definer: проверка секрета,
           Turnstile-токен         Turnstile siteverify,              лимиты, повторная валидация, вставка,
                                   хэш IP                             номер, бриф v1, токен клиента
```

- Функция `submit_project_request` доступна анонимной роли, но **без верного серверного секрета ничего не делает**.
  Иначе спамер вызвал бы её напрямую публичным ключом в обход Turnstile и лимитов. Секрет (`INTAKE_SUBMIT_SECRET`)
  хранится только в Vercel (серверная переменная) и в приватной таблице БД (задаётся SQL-командой, не миграцией).
  Это узкий ключ на одно действие вместо полного серверного ключа Supabase (решение 1).
- **Turnstile** (Cloudflare, бесплатно, без «картинок»): включается, если заданы ключи; без них форма работает
  на остальных мерах.
- **Лимиты в БД** (`intake_rate`): по хэшу IP (sha256 с солью, сам IP не хранится) — 3 заявки за 10 минут и 10 в сутки,
  плюс общий предохранитель 200 в сутки на пространство.
- **Ловушка**: скрытое поле, которое заполняют только боты; отправка быстрее 8 секунд после открытия формы считается
  подозрительной.
- **Повторная отправка**: форма шлёт `idempotency_key` (uuid черновика); тот же ключ возвращает ту же заявку,
  второй заявки не будет.
- **Размеры**: тело ≤ 64 КБ (проверка в action и в функции), конкурентов ≤ 10, референсов ≤ 10, ссылок ≤ 15.
- **Инъекции**: только параметризованные вызовы Supabase; тексты нигде не рендерятся как HTML (React и PDF выводят
  текст); URL — только `http(s)`.

## 6. Файлы

**В первой версии — только ссылки** (Figma, Google Drive, Dropbox, сайт): у клиента материалы и так лежат в облаке,
а открытая загрузка файлов анонимами — самая рискованная часть всей фичи. Таблица `project_request_files` и приватный
бакет проектируются сразу, включаются отдельной фазой: PDF/PNG/JPEG/WebP, ≤ 10 МБ на файл, ≤ 5 файлов, имя файла
заменяется на uuid, MIME проверяется по содержимому на сервере, загрузка через одноразовый подписанный URL,
выданный только после успешной отправки заявки (решение 3, §16).

## 7. PDF «Бриф проекту»

- Движок: **`@react-pdf/renderer`** в серверной функции Next.js. Чистый JS: работает на Vercel без Chromium
  (Chromium на Vercel — ~50 МБ и медленный холодный старт). Шрифты Manrope и IBM Plex Mono в формате TTF с кириллицей кладутся
  в репозиторий (лицензия OFL), вёрстка — в стиле сайта и резюме (SIGNAL: моно-подписи, нумерация разделов «01 / …», тонкие линии).
- Источник истины — **снимок в `project_request_documents`**, а не файл. PDF собирается из снимка по запросу.
  Шаблон версионируется (`template_version`), поэтому один и тот же снимок даёт тот же документ. Отдельно хранить
  файл не нужно, а значит, нет и публичных ссылок на файлы.
- Имя: `Project-Brief-{project-name}-{YYYY-MM-DD}.pdf` (латиница: имя транслитерируется), заголовки ответа
  `Content-Disposition: attachment`, `X-Robots-Tag: noindex`, `Cache-Control: private, no-store`.
- Содержание: как в постановке (номер, дата, версия, клиент, проект, обзор, аудитория, конкуренты, референсы, скоуп,
  материалы, бюджет, сроки, доп. информация) + оговорка внизу: документ фиксирует исходные данные клиента и не является
  объёмом работ, договором, сметой или ТЗ. Языки — uk и en.
- **Доступ клиента** без аккаунта: при отправке функция создаёт случайный токен (32 байта), в БД хранится только его хэш,
  срок — 30 дней. Токен возвращается один раз в ответе и живёт на экране подтверждения (в памяти и sessionStorage вкладки,
  не в URL). Скачивание: `POST /api/project-request/brief` с токеном → функция `get_request_brief(code, token)` отдаёт снимок
  → PDF. Дизайнер скачивает из инструмента по членству в пространстве.
- «Поделиться»: на телефоне — системное меню «Поделиться» с PDF-файлом (Web Share API), на компьютере — скачать.
  Отправлять дизайнеру не нужно: заявка уже в инструменте, PDF — копия для клиента.

## 8. Форма (публичная часть)

Маршруты: `/uk/start-project`, `/en/start-project`; индексируются, свои title/description/canonical/hreflang/OG.
Подтверждение — состояние той же страницы, без отдельного URL с данными клиента.

Шаги (прогресс «3 / 9», назад/далее, фокус на заголовок шага при переходе, ошибки под полем и сводкой вверху):

1. **Що потрібно** — типы (несколько), «Інше» → поле; название или «Ще немає назви».
2. **Чинний продукт** — є/немає; если есть: адрес, описание, что работает, что не нравится, что поменять, ссылки (сайт, App Store, Google Play, Figma, Behance, Dribbble, інше). Предупреждение: не присылайте паролей.
3. **Про проєкт** — коротко, что делает, какую проблему решает, почему сейчас, цели (чипы + «Інше»).
4. **Аудиторія** — кто пользуется, основные пользователи, гео, B2B/B2C/внутренний, демография (если важна), боли — простыми словами с подсказками.
5. **Конкуренти й референси** — «знаю/не знаю»; карточки конкурентов (+ додати, ≤ 10); референсы дизайна с «що подобається».
6. **Обсяг робіт** — услуги чипами + «Не знаю — потрібна ваша порада».
7. **Матеріали** — что уже есть (чипы) + ссылки.
8. **Бюджет і терміни** — диапазон из конфига, валюта (USD/EUR/UAH), «своя сума» → поля; старт, дедлайн так/ні → дата и причина.
9. **Контакти й побажання** — имя*, email*, компания, роль, телефон, Telegram, сайт, удобный канал; «Що ще варто знати?».
10. **Перевірка** — бриф целиком, «Змінити» у каждого раздела, согласие (не отмечено заранее, ссылка на политику), «Надіслати заявку».

Контакты — в конце (по схеме из постановки): человек сначала рассказывает о проекте и только потом оставляет данные.
Раздел 4 постановки ставит контакты первым шагом; выбрать порядок — решение 4.

Условная логика: нет продукта → вопросы о нём скрыты; «не знаю конкурентов» → карточек нет; нет дедлайна → дата
не обязательна; «своя сума» → поля суммы; «Інше» → поле пояснения. Скрытые ответы не отправляются.

Черновик: `localStorage` с версией схемы, срок 7 дней, **без шага контактов** (имя, email, телефон в браузере не
храним). При возврате — «Продовжити з місця, де зупинились» / «Почати заново». Очищается после отправки.

Бюджеты, валюты, типы, услуги, цели, материалы — один конфиг `src/domains/requests/config.ts` (ключи + границы),
подписи — в словарях uk/en. Ключи пишутся в БД, поэтому переименование подписи не ломает старые заявки.

CTA — одна формулировка: **«Обговорити проєкт» / «Discuss a project»**. Места: шапка (кнопка), главная (основная
кнопка рядом с «Написати мені»), конец кейса, «Про мене», подвал. «Написати мені» остаётся для быстрых вопросов.

## 9. Инструмент: раздел «Заявки»

Маршруты в текущей структуре: `/w/{ws}/requests` (список) и `/w/{ws}/requests/{code}` (карточка);
на странице пространства — вкладки «Проекты · Заявки · Клиенты» со счётчиком новых.

- **Список**: клиент, проект, тип, бюджет, сроки/дедлайн, дата, статус; фильтры по статусу (по умолчанию — новые
  и в работе), архив отдельно; сортировка — новые, бюджет, дедлайн.
- **Карточка**: все разделы брифа с подписью «Данные клиента»; конкуренты, референсы, ссылки; заметки (только внутренние);
  документы с версиями и «Скачать PDF (uk/en)»; действия — статус, заметка, «Сделать проектом», архив, удаление (owner);
  «Написать клиенту» — `mailto:`/Telegram-ссылка, сам инструмент ничего не отправляет.
- **Клиенты** (минимально): список клиентов и их заявок; база для будущего портала.

Удаление: заявка удаляется каскадом вместе с конкурентами, референсами, ссылками, заметками, документами (и файлами
фазы 2 — через очистку хранилища). Заявку со статусом `converted` удалить нельзя (`restrict`), только архивировать:
она — история проекта. Удаление клиента запрещено, пока у него есть заявки; для запроса «удалите мои данные» —
функция `forget_client`: стирает контакты и тексты, оставляет обезличенную запись для связанных проектов.

## 10. Уведомления

Абстракция `notify(event)` в `src/domains/requests/notify.ts` с адаптерами; без настроек — тихо пропускает и пишет в лог.

- **Дизайнеру о новой заявке**: только номер, тип, диапазон бюджета, сроки, кнопка «Открыть заявку» — без контактов
  и текстов. Варианты: Telegram-бот (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`) — работает сразу, без домена;
  или e-mail через Resend (`RESEND_API_KEY`) — без своего домена Resend шлёт только на почту владельца аккаунта,
  этого достаточно для уведомлений (решение 2).
- **Клиенту** «Ваш бриф проекту» — только после подключения домена (нужен проверенный отправитель). До тех пор клиент
  получает PDF на экране подтверждения. Если отправка не удалась, заявка всё равно сохранена: письмо — уведомление,
  а не хранилище.

## 14. Настройка (production)

1. Применить миграцию `20261007000017_project_requests.sql`.
2. Секрет: `openssl rand -hex 32` → значение в Vercel как `INTAKE_SUBMIT_SECRET` (Production, тип Sensitive),
   его хэш — в базу (SQL Editor, не миграция):
   ```sql
   insert into private.intake_secret (secret_hash)
   values (encode(sha256(convert_to('<секрет>', 'UTF8')), 'hex'))
   on conflict (id) do update set secret_hash = excluded.secret_hash, updated_at = now();
   ```
   Смена секрета — та же команда и новое значение в Vercel; старый перестаёт работать сразу.
3. Принимающее пространство: `insert into intake_settings (workspace_id) values ('<id пространства>');`
   Выключить форму: `update intake_settings set enabled = false;` — сайт покажет «форма временно недоступна».
4. Turnstile: Cloudflare → Turnstile → Add site (домен `product-designer-workspace.vercel.app`, режим Managed) →
   `NEXT_PUBLIC_TURNSTILE_SITE_KEY` и `TURNSTILE_SECRET_KEY` в Vercel.
5. Resend: аккаунт на почту владельца → API key → `RESEND_API_KEY`, `INTAKE_NOTIFY_EMAIL` (та же почта).
6. Redeploy production.

## 15. Что не сделано (осознанно)

- **Загрузка файлов клиентом** — только ссылки (решение 3, §16). Таблица и бакет — отдельной фазой по §6.
- **Письмо клиенту** «Ваш бриф» — нужен свой домен для отправителя Resend; до тех пор PDF — на экране подтверждения.
- **Страница «Клиенты»** — клиенты хранятся и переиспользуются, но отдельного списка в инструменте пока нет.
- **«Забыть клиента»** (обезличить контакты при запросе на удаление, сохранив проект) — сейчас: удалить заявку
  (клиент удаляется вместе с последней заявкой); у заявки, ставшей проектом, контакты стираются вручную в SQL.
- **Новые редакции документов** (скоуп, смета, договор) — тип и версии в таблице есть, интерфейса нет.
- **Текст политики конфиденциальности** — черновик, требует проверки владельцем/юристом (§12).

## 16. Решения владельца (1 октября 2026)

1. **Секрет публичной отправки** — узкий `INTAKE_SUBMIT_SECRET` (одна функция), не полный серверный ключ.
2. **Уведомления** — e-mail через Resend на почту владельца (без своего домена Resend пишет только ей).
3. **Файлы** — в первой версии только ссылки; загрузка — отдельной фазой.
4. **Контакты** — последним шагом перед проверкой.
5. **Бюджет** — видят участники пространства.
6. **Turnstile** — подключаем; без ключей форма работает на ловушке и лимитах.
